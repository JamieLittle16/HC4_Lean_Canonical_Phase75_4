# Canonical owners and reuse registry

This file exists to prevent duplicate infrastructure.

Before introducing a new definition, structure, theorem family, support filter, state transition, or helper with a generic-looking name, search this registry and the generated declaration index. The file named here is the **canonical owner** of the concept; downstream modules should import and adapt it rather than redeclare it.

This registry is intentionally selective: it lists concepts with high reuse or high collision risk. The exhaustive declaration list is generated by `tools/generate_proof_inventory.py`.

### Dependent facet predicates

`MvRankThreeOnFacet F d` reduces by matching on `F`. If Lean refuses projections such as `h.1` because `F` is unresolved, either:

```lean
have hcoords := (HC4.Newton.mvRankThreeOnFacet_iff F d).1 h
```

or perform:

```lean
cases F <;> ...
```

Do not create a second rank-three predicate merely to avoid the dependent match.

## 4. Cross-facet line/ray infrastructure

There are two owners because there are two mathematically distinct assumption sets.

### Balanced affine-line route

Owner:

- `HC4/Newton/FirstContactCrossFacetAffineLine.lean`

Canonical helper includes:

- `CrossFacetInitialData.face_weight_eq`
- balanced/contact/secondary-equation affine proportionality.

Use this route when the carrier genuinely has the required torus-balance equation.

### Balance-free finite-support ray route

Owner:

- `HC4/Newton/FiniteSupportCrossFacetRay.lean`

Canonical objects include:

- `CrossFacetRayData`
- `crossFacetRayData`
- `CrossFacetInitialData.ray_face_weight_eq`
- `CrossFacetInitialData.auxiliary_cross_proportional`.

The specialized helper name `ray_face_weight_eq` is intentional. It prevents collision with the already-existing balanced helper `CrossFacetInitialData.face_weight_eq` when both modules are imported.

**Naming rule:** if a helper belongs only to one refinement/route, include the refinement in its name. Do not take a generic fully-qualified theorem name already owned by another module.

## 11. Namespace and declaration rules

### 11.1 Search the fully-qualified namespace before declaring

For a proposed declaration `Foo.bar`, search both:

```bash
rg -n '(^|\s)(theorem|lemma|def|structure|inductive|abbrev).*bar\b' HC4
rg -n 'bar\b' HC4
```

and inspect `docs/generated/DECLARATION_INDEX.md`.

Lean can compile two source files independently and only report a duplicate fully-qualified environment declaration when a later module imports both. This is exactly why duplicate helpers are dangerous in a large DAG.

### 11.2 Prefer the more specialized new name

If an older API already owns a reasonable generic name, keep it stable and give a newer route a qualified/specialized name, e.g.

```text
face_weight_eq              -- older balanced affine-line owner
ray_face_weight_eq          -- balance-free ray-specific helper
```

### 11.3 Definitions live with their representation

Examples:

- polynomial exponent predicate → `HC4.Polynomial`;
- Newton carrier/exposure → `HC4.Newton`;
- state/progress/provenance → `HC4.Valuation`;
- terminal rational contradiction → `HC4.RationalRigidity`.

Do not move a concept into the namespace of its most frequent consumer.

## 12. Adapter versus owner

A good final-assembly file usually does one of four things:

1. **Owner:** introduces a genuinely reusable representation or theorem.
2. **Carrier:** packages already-proved facts about one exact object.
3. **Adapter:** translates one established interface into another without new mathematics.
4. **Reduction/assembly:** performs an exhaustive split and dispatches branches to existing owners.

Before adding a fifth version of a concept, decide which category the new file belongs to. If it is an adapter, it should normally contain very little foundational algebra.
